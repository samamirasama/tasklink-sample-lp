# 実機技術検証プロトコル（共有拡張→保存→本体で取得）

- 作成日：2026年10月2日（金）
- 目的：`01_結論と評価.md` 5.2 の「実機で確かめる項目」を、順番に、記録表つきで実施できるようにする。MVPの実装ではなく、**検証用の最小コード（スパイク）**を使う。
- 前提（未確認・要回答）：Mac（Xcode 26以降、iOS 26 SDK）、検証用iPhone（Foundation Models の確認には iPhone 15 Pro 以降と推定）、Apple Developer Program（App Groups 等の機能を使うため有料アカウントを推奨。無料のPersonal Teamで App Groups が使えるかは未確認）。
- 所要：準備1日、計測1〜2日。
- 付属：`spike/` に Swift ソース3本。**本環境ではコンパイルしていない**ため、Xcode上でエラー修正が必要になる前提。

## 1. 準備（Xcode、一工程ずつ）

1. Xcode で「File → New → Project → iOS → App」を選び、名前を `AtoSpike`、Interface を SwiftUI、Language を Swift にして作成する。
2. 「File → New → Target → iOS → Share Extension」を選び、名前を `AtoShare` にして追加する。Activate のダイアログは「Activate」。
3. 両ターゲットの「Signing & Capabilities」で「+ Capability → App Groups」を追加し、同じ識別子（例 `group.jp.example.atospike`）を両方に入れる。
4. `AtoShare/Info.plist` の `NSExtension → NSExtensionAttributes → NSExtensionActivationRule` を、文字列型から辞書型に変え、次のキーを入れる：`NSExtensionActivationSupportsWebURLWithMaxCount = 1`、`NSExtensionActivationSupportsImageWithMaxCount = 5`、`NSExtensionActivationSupportsText = YES`、`NSExtensionActivationSupportsFileWithMaxCount = 1`。
5. `AtoShare/ShareViewController.swift` を `spike/ShareViewController.swift` の内容で置き換える。`SLComposeServiceViewController` ではなく `UIViewController` 継承にする（Storyboard を使う設定なら、MainInterface.storyboard のクラス名を合わせる）。
6. `spike/SharedStore.swift` を両ターゲットに追加する（Target Membership で両方にチェック）。
7. `AtoSpike/ContentView.swift` を `spike/ContentView.swift` の内容で置き換える。
8. 両ソースの `appGroupID` を手順3の識別子に合わせる。
9. iPhone を接続し、`AtoSpike` スキームで実機にインストールする。初回は iPhone 側で開発者を信頼する設定が必要。
10. 共有シートに `AtoShare` が出ることを Safari で確認する（出なければ共有シートの「その他」で有効にする）。

## 2. 試験A：共有元別の受信データ（最重要）

各共有元で共有 → `AtoShare` を選ぶ → 本体 `AtoSpike` を開いて記録を見る。1回ごとに下表へ記入する。

| 共有元 | 操作 | 記録する項目 |
|---|---|---|
| Safari（Webページ） | 共有ボタン → AtoShare | 型識別子一覧、URLの値、URLがURL型かData型か、付随テキスト、保存までの秒数 |
| Safari（画像の長押し共有） | 画像長押し → 共有 → AtoShare | 画像の型（public.image／public.jpeg／file-url）、サイズ、保存成功 |
| Instagram（投稿） | 紙飛行機 → 共有先 → AtoShare | URL形式（instagram.com/p/…か）、テキストの有無 |
| Instagram（リール） | 同上 | 同上 |
| X（投稿） | 共有 → 「他の方法で共有」→ AtoShare | URL（x.com か twitter.com か）、本文テキストの有無 |
| YouTube（アプリ） | 共有 → その他 → AtoShare | URL（youtu.be か）、タイトルの有無 |
| TikTok | 共有 → その他 → AtoShare | URL（短縮か）、型（url か plain-text か） |
| 写真アプリ（スクショ1枚） | 共有 → AtoShare | 型、サイズ、保存秒数 |
| 写真アプリ（スクショ5枚） | 同上 | メモリ警告・クラッシュの有無（Xcode のデバッグゲージで拡張のメモリを見る） |
| メモ（テキスト選択） | 選択 → 共有 → AtoShare | plain-text の内容 |

**合否の目安**
- 10件すべてで「拡張が1秒以内に閉じ、本体で記録が見える」こと。
- Instagram／X／TikTok で URL が取れない場合は、plain-text から URL を抽出する処理が必要になる。これは設計変更であり、記録して `01` の仕様に反映する。
- スクショ5枚でクラッシュする場合は、拡張内での縮小保存または枚数上限が必要。

## 3. 試験B：本体でのメタデータ取得（LinkPresentation）

1. 本体の一覧で、試験Aで保存した各URLの「メタデータ取得」を押す。
2. タイトル・画像が取れたか、所要秒数、エラー内容を記録する。
3. 特に Instagram・X・TikTok の結果を見る。ログインページのタイトルになる、またはエラーになるなら「ログイン必須ページは未取得表示」の方針で確定する。

|---|---|---|---|---|

## 4. 試験C：端末内OCR（Vision）

1. 本体の一覧で、試験Aで保存したスクショの「OCR」を押す。
2. `supportedRecognitionLanguages` に `ja` が含まれるかの表示を記録する。
3. SNSのスクショ（日本語、横書き）で認識結果を目視評価し、「店名・価格・日付が読めるか」を記録する。
4. 機内モードで同じ操作を行い、オフラインで動くかを記録する。

## 5. 試験D：端末内LLM（Foundation Models）

1. 本体の「LLM可用性」を押し、`availability` の結果（available／appleIntelligenceNotEnabled／deviceNotEligible／modelNotReady）を記録する。
2. available の場合、保存した1件の本文（タイトル＋共有テキスト）を `contentTagging` で分類させ、返ったタグを記録する。日本語のタグ品質を目視評価する。
3. 日本語の長文（2,000文字程度）を渡し、コンテキスト超過エラー（4,096トークン）が出るかを記録する。

## 6. 試験E：バックグラウンドと通知

1. 拡張から保存したときに本体へ誘導するローカル通知が届くか（本体で通知権限を許可済みの状態で）。
2. 本体で `BGProcessingTask` を登録し、実際に実行された時刻をログに残す。24時間での実行回数と遅延を記録する。
3. 本体で「解析開始」を押してから即ホームに戻り、`BGContinuedProcessingTask` が継続したか（Live Activity の表示、完了までの秒数）を記録する。

## 7. 試験F：容量・書き出し

1. スクショ100件を保存し、設定→一般→iPhoneストレージでアプリ容量を記録する（原寸保存と縮小保存の両方）。
2. 書き出し（JSON）→ アプリ削除 → 再インストール → 読み込みで、全件復元できるかを記録する。
